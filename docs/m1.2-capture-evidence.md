## What the repair changes

New launches keep two views of the same redacted output:

- the execution log stays a bounded prefix (`LAUNCH_STREAM_LIMIT`, 2 MiB),
  with the same redaction as before;
- adapters parse the full redacted stream, so a `thread_id`, `session_id`,
  or usage object the process actually wrote is visible even when that
  object sits past the log prefix.

Session ids are taken only from codex `thread.started.thread_id` and
cursor envelope `session_id`, and only when the value is a non-empty
string without whitespace. `request_id`, numeric ids, and missing fields
stay NULL. `ORX_SESSION_REF` is still a host stamp and is not copied onto
CLI attempts.

Codex keeps the last `turn.completed` usage object and does not add earlier
turns together. Cursor stores `cacheReadTokens` as reported, including
when it is larger than `inputTokens`. Exact accuracy requires input,
output, and cached to all be present non-negative integers. A missing
field stays NULL and the accuracy is `unknown`. A present but unusable
field (string, float, boolean, negative) stores nothing.

A finished CLI attempt with no storable observation records one reason:

| Reason | Evidence |
|---|---|
| `adapter_unsupported` | the adapter has no usage hook (shell) |
| `harness_omitted` | the hook saw a finished stream and no usage event |
| `malformed_output` | a usage event or envelope was present and not usable |
| `truncated` | the parsed text itself ends in the capture truncation marker and no usage object survived |
| `execution_failure` | the launch failed or never started, and the stream did not carry a usable usage object |

A launch that fails after emitting a real usage object still stores that
object and its session id. The log bound is not, by itself, a `truncated`
miss: truncation is recorded only when the text the parser could see was
cut.
