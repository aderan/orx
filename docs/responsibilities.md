# ORX 职责与边界

状态：职责基线，2026-10-03。适用于后续功能取舍；当前能力以代码和 M0/M1 实施契约为准。本次只明确产品职责，不改变运行行为，也不把候选能力列为已实现。

## 一句话定义

**ORX 用于控制 agent 的调度，组织它们执行 Goal 中的任务，并依据证据与验证结果记录完成状态。**

服务对象是个人开发者及其宿主 agent。用户从“我要达到什么结果”开始，日常关注进展、阻塞和验收；执行工具、模型与运行环境通过配置接入。

ORX 的核心价值是：换一个 agent 或换一个宿主，仍能知道 Goal 是什么、当前计划是哪版、谁完成了什么、哪些检查通过、下一步受什么阻塞。

## 责任分配

| 参与者 | 负责什么 | 边界 |
| --- | --- | --- |
| 用户 | 定义目标、约束、验收与授权；解决影响目标的歧义 | ORX 不替用户生成新的产品目标或扩大授权 |
| Controller | 读状态、调用规划、推进调度、处理失败、触发验证与重规划、必要时升级给用户 | 决策在 Goal 范围内；通过 ORX 提交状态变化 |
| Planner | 探索项目、必要时研究、形成方案、拆任务、设计验证 | 输出结构化计划；不拥有长期调度状态 |
| ORX | 校验计划、路由执行配置、指派工作、维护状态、运行约定检查、记录结果 | 执行确定规则；不替 agent 作领域推理 |
| Worker | 完成指定任务；实现、测试、研究、文档或其他已授权工作；提交证据 | 不自行改 Goal、扩任务范围或宣布整个 Goal 完成 |
| Verifier | 按指派要求检查结果，给出判断和原因 | 判断来自检查结果；不重新定义验收条件 |
| 执行工具与环境 | 提供模型调用、工具操作、登录、权限与实际工作环境 | ORX 通过适配契约接入，不重建这些能力 |

同一宿主可以承担不同角色，但每次指派的责任必须明确。ORX 维护执行事实，Controller 消费这些事实并推进流程；Controller 的聊天判断不能直接替换运行状态。

当前 Controller 在宿主中运行；`orx run` 返回后由宿主继续推进。配置中的 controller profile 尚不代表 ORX 已实现内置常驻 Controller。

## ORX 执行什么

### 1. 接纳和维护 Goal

保存 objective、constraints、acceptance、context 及其状态，建立执行记录。外部事件先进入 Inbox，再经手工接纳或显式配置的接纳策略建立 Goal。

外部 Issue 是工作来源，不自动代表已授权执行。当前 `watch` 负责收取候选；即使配置 auto_accept，它也只建立 Goal，不自动启动规划和 worker。

### 2. 组织规划，校验任务图

向 Planner 提供目标与计划契约；接受 Plan IR，并检查任务标识、依赖、循环、scope、能力要求和验收覆盖。只有生效的计划修订参与调度，旧版未完成任务在替换时取消。

ORX 检查计划是否满足结构和规则。方案是否合理、任务是否真正覆盖业务目标，由 Planner 和相应验证负责。当前要求每条 Goal 验收原文出现在至少一个任务的 acceptance 中；这种覆盖检查不等于语义证明。

### 3. 选择执行配置，交付指派

依据角色、能力、规划深度、静态偏好与可用性选择 profile，记录选择原因。明确指定的 profile 遵守固定选择契约；fallback 只沿允许的配置顺序发生。

CLI driver 由 ORX 启动执行工具；host driver 返回宿主指派并通过 claim/result 交接；external driver 停在等待外部交付的状态。宿主内部启动子 agent 的方式由宿主承担。

### 4. 管理执行状态与恢复入口

维护依赖解锁、任务状态转换、执行尝试、失败原因与证据关联。CLI 执行有超时、输出采集和结果记录；失败反馈进入后续指派。

ORX 提供 retry 和 replan 的合法入口与状态约束：retry 重新执行当前任务，replan 更换任务图。何时使用、是否改用其他配置、是否需要用户澄清，由 Controller 或操作者决定。当前没有进程内自动重试循环。

### 5. 组织验证与收敛

运行计划指定的命令检查，指派 agent 检查并接收结论。任务执行结束进入验收流程，只有按验证契约通过的任务才成为 `passed`；当前生效计划的所有任务通过，Run 才成为 `done`。

验证列表为空时，现有契约允许任务在提交完成后通过，没有额外的独立检查。需要独立审查或整体验收的 Goal，必须在计划中明确相应检查或最终验收任务，不能把 `done` 当成 ORX 自行理解了自然语言目标。

### 6. 提供可追溯的运行事实

保存计划修订、路由、attempt、状态事件、证据与验证；通过 status、timeline、usage、agent status 暴露事实。用量来自实际观测，并标明精度；缺失的 token 数不当作零。

能力探测、错误分类和冷却状态服务于可调度性。ORX 不据此承诺精确余额、未来成功率或模型效果排名。

## ORX 不执行什么

以下是产品边界，不是“以后把这些都补齐”的路线图。

| 不承担的职责 | 可接入的协作方式 |
| --- | --- |
| 亲自进行领域研究、架构推理、编码或视觉判断 | 调度 Planner、Worker、Verifier；保存其产物与结论 |
| 提供模型推理服务、agent 工具循环或通用 agent 框架 | 接入已有 agent CLI、宿主或外部执行者 |
| 替用户决定产品方向、业务优先级、Goal 范围 | 接受用户定义或已授权策略选出的 Goal |
| 建造 IDE/ADE：编辑器、文件树、多终端工作台、浏览器、agent 聊天界面 | 调度状态可展示；交互、调试和精修留在现有工作工具 |
| 提供团队项目管理、Issue Tracker、CRM 或通用自动化平台 | 把与 Goal 有关的事件标准化为 Inbox 候选 |
| 接管供应商登录、订阅、账号轮换与凭据存储 | 查询已有工具的认证状态，记录 auth_required 并提示处理 |
| 提供通用云主机、容器平台或任意环境运维 | 后续执行 driver 可接入已有隔离环境 |
| 提供通用 Git/worktree 管理、冲突解决或代码合并判断 | 后续可管理与任务绑定的工作区生命周期；集成工作交给已指派 agent |
| 因额度剩余自行发明工作，或无限并行、无限重试 | 只执行已接纳 Goal；容量策略必须有任务依据、资源约束与停止条件 |
| 自动获得发布、部署、推送、合并或发信权限 | 这些动作可作为明确授权的任务，由具备能力的执行者完成 |
| 维护跨项目的通用个人记忆或知识库 | 保存本次 Goal 的上下文、执行历史与证据；长期知识由外部系统提供 |
| 把持续研究竞品变成每个用户运行都执行的功能 | 参考项目研究属于 ORX 仓库自身的工程维护，或某个用户明确指定的研究 Goal |

具体工作类型可以扩展，ORX 核心仍围绕调度。研究、测试、文档、UI 审查、迁移或发布不需要各自新增一套角色系统；它们由任务内容、所需能力、证据与验证要求区分。

## 用场景检验边界

| 场景 | ORX 的动作 | agent / 用户的动作 |
| --- | --- | --- |
| “完成某项目 M2” | 建立 Goal，指派规划，执行已提交任务图并记录验收 | 用户提供结果要求；Planner 判断方案和拆分 |
| “研究接口并写报告” | 指派研究任务，关联报告与验证结果 | Worker 查资料写报告；Verifier 核查来源和内容 |
| worker 报完成，测试失败 | 记录失败，不解锁依赖任务 | Controller 选择修复重试；Worker 修复 |
| 实现发现架构假设错误 | 保留失败依据，检查 replan 状态条件，接纳新计划修订 | Controller 提请 Planner 重规划；涉及 Goal 变化时交给用户 |
| 模型额度耗尽 | 记录健康状态；后续路由按允许的配置顺序选择 | Controller 决定等待或再次推进；用户处理订阅与登录 |
| 新 GitHub Issue 到达 | 去重并进入 Inbox；接纳后关联 Goal | 用户或预设策略决定接纳；宿主推进执行 |
| 两个任务修改同一文件 | 当前 CLI 串行；未来并行需明确冲突与隔离准入规则 | Planner 消除共享写入；宿主对自行并行负责 |
| GUI agent 没有启动接口 | 等待 external 交付；不宣称已自动执行 | 外部操作者启动工具并按协议提交结果 |
| Goal 要求发版 | 调度明确授权的发布任务，记录结果与证据 | 发布执行者使用现有工具；需要的授权来自用户或既有政策 |
| 状态显示 done，但缺少部署或最终审查 | 反映当前计划已通过的事实 | 需要的步骤应进入验收任务；用户与 Planner 不能省略后再期待 ORX 猜到 |

## 候选能力如何归属

这些是方向判断，不是本次新增承诺。M1 完成记录中的 M2 候选需要重新按职责筛选，不能仅因为记入 backlog 就自动实施。

| 候选能力 | 归属判断 |
| --- | --- |
| 有界重试、冷却后的再调度、执行中断恢复 | 属于调度可靠性；需明确失败类型、尝试上限、状态一致性与停止规则 |
| 并行与 worktree driver | 属于任务执行能力；需依赖、写入冲突、隔离、集成验证与清理契约；不扩成通用工作台 |
| `replan --context-file` | 属于指派上下文交付，帮助 Planner 理解本轮意图 |
| Linear 或其他来源 | 可作为薄 Source 接入 Inbox；不承担来源系统的业务流程 |
| webhook、定时器、用户级后台服务 | 仅在持续接纳或推进 Goal 的需要成立时加入；不扩成通用事件自动化平台 |
| 更广的能力声明和执行工具适配 | 属于可替换执行者；先验证真实调用与结果契约 |
| 配额与成本上限 | 属于执行约束；要求可信观测，不能把推测余额当成事实 |
| TUI、Web 状态页、通知 | 可薄展示进度、阻塞与必要操作；不引入编辑器、终端或聊天工作空间 |
| 完整 IDE、账号池运营、项目管理 SaaS、通用知识库 | 超出职责，即使其他 agent 产品支持也不作为追赶目标 |

## 新功能准入问题

每个提案必须写清楚：

1. 它解决 Goal → Plan → Task → Attempt → Evidence → Verify 中哪个具体问题？
2. ORX 是否需要成为这个事实或状态的权威？现有 agent、执行环境或外部系统是否已经承担了它？
3. 输入、输出、失败、等待、停止与验收分别是什么？
4. 换一个 agent 或模型，这个功能和它保存的事实是否仍成立？
5. 能否通过薄适配、明确任务或现有工具完成，避免引入另一套业务系统？

直接改善 Goal 的可调度性、可恢复性或可验收性，并有清晰契约的能力，可以进入核心。只需对接外部系统的能力放在适配层；与某次任务内容有关的工作交给 agent；没有这些关联的提案不纳入 ORX。

## 当前实现与职责承诺的差距

- 当前每个项目只允许一个 active Goal；每个 Run 只有一版 active plan。
- CLI 执行有效并行度为 1；没有自动创建 worktree、并行集成或合并冲突机制。
- host 指派由宿主认领并完成；external 指派等待外部提交；ORX 不原生启动 host 子 agent。
- 状态持久化允许后续读取事实，但不等于进程断线后自动重连、续跑或完整崩溃恢复。
- `scope.allowed` 当前用于路径校验和指派约束，尚不构成文件级强制隔离；命令检查的固定目录、超时和拒绝规则也不是完整沙箱。
- 内置 agent 适配包括 Codex、Cursor 和 shell；任务能力按配置声明匹配，声明本身不证明执行工具拥有该能力。agent 验证的括号能力语法目前只支持 `agent[vision]:`。
- GitHub 来源通过已有 `gh` 获取 Issue；没有自动评论、关 Issue、建 PR 或双向状态同步。
- 对复杂结果的语义验收来自显式指定的 agent / host 检查，ORX 不自行解释自然语言验收。
