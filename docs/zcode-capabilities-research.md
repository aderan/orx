# ZCode subagent capabilities: evidence and integration limits

Research date: 2026-10-04 (Asia/Shanghai). Scope: official public documentation and installed application version metadata; no user sessions, logs, credentials, or model configuration inspected. No runtime delegation test performed.

## Finding

ZCode already documents native subagents. ORX should investigate a host-driven delegation integration before assuming that a standalone ZCode CLI is required. This is an architectural recommendation, not a statement that ORX already implements it.

## Confirmed native delegation capabilities

The following is a compact paraphrase of the official [Subagents documentation](https://zcode.z.ai/cn/docs/subagents):

| Boundary | Documented behavior |
| --- | --- |
| Context | Independent context; results return to the parent conversation. |
| Dispatch | Parent uses its Agent tool; children cannot dispatch further children. |
| Roles | Built-in general-purpose has full tools; Explore is read-only. Custom user roles are Beta. |
| Models | Explicit model or inheritance; built-in roles also allow independent model selection. |
| Effort | `thoughtLevel` applies only with an explicit supported model. Inherited models inherit parent reasoning. Unknown `reasoningEffort` is silently ignored. |
| Definitions | User definitions: `~/.zcode/agents/<name>.md`; required `name` and `description`; optional `maxTurns`. |
| Reload | Definition/config changes require a new session; inherited models follow parent model changes. |
| Permissions | `tools` / `disallowedTools` restrict available tools. Custom allowlists require exact MCP tool names. |
| MCP | Only services connected at parent session start are visible; declared missing services fail invocation. |
| Project rules | Since v3.7.1, user/workspace AGENTS.md injection defaults on; Explore defaults off. |
| Concurrency | Multiple foreground children run concurrently and parent waits; background completion returns automatically. Numeric concurrency ceiling unspecified. |

This proves role-specific model selection is a supported product capability. It does not prove any particular installed session has these roles configured or that an ORX profile controls them.

## GLM 5.3 and Flash availability

The official [Connect Models documentation](https://zcode.z.ai/cn/docs/configuration) lists GLM-5.3 and GLM-5.3-Flash as built-in models for BigModel and Z.ai account connections; API-key model availability depends on account permissions and the provider model list. The documentation presents Flash as multimodal-capable. It does not establish Flash's effectiveness as an ORX verifier, comparative verification accuracy, or a stable numerical price advantage for this user's account.

**Not verified:** the provider-qualified value accepted by the subagent `model` field for these built-ins, Flash's selectable reasoning levels, and the actual provider request generated by a chosen `thoughtLevel`. A display name or provider API model name is insufficient evidence for a ZCode subagent identifier. Select the concrete model in the installed client, inspect the generated agent definition, and validate in a fresh session before generating an installer with fixed IDs.

The official [ZCode Agent documentation](https://zcode.z.ai/cn/docs/agents) describes three GLM-5.3 UI reasoning levels: low, high, and highest, with highest the default. ORX's five-level vocabulary needs an explicit provider mapping; it should not assume every ORX level is accepted unchanged.

## Distribution and connection direction

[Plugin documentation](https://zcode.z.ai/cn/docs/plugin) confirms that a plugin can bundle skills, commands, agents, MCP servers, and hooks. Subagents use `agents/*.md`; the manifest supports an `agents` component, and plugin agents appear as read-only definitions in the settings panel. Plugins can be distributed through a local, Git, or GitHub-backed market. This supports an ORX package containing controller instructions and reusable worker/verifier roles rather than relying only on copying SKILL.md files.

[MCP documentation](https://zcode.z.ai/cn/docs/mcp-services) documents external tools connected **into** ZCode. It does not describe an external API that makes ZCode spawn agents. An ORX MCP service can expose claim, heartbeat, submission, and state operations for the host to call; this must not be confused with ORX obtaining the host's native Agent tool itself.

## Lifecycle and isolation not established

The reviewed official pages do not provide an Agent-tool invocation/return schema, stable child identity contract, cancellation API, resume API, restart recovery guarantees, or per-child working-directory/worktree binding. Foreground/background behavior is documented, but it does not answer these integration questions. Independent conversation context is not evidence of isolated filesystems or separate Git working trees.

[Safety confirmation documentation](https://zcode.z.ai/cn/docs/safety-confirm) describes task-level permission modes and persistent approval requests. It does not establish a separate sandbox or per-child permission mode. Giving a verifier Bash access to execute tests also enables commands that can modify files; a tool allowlist alone should not be represented as filesystem write isolation.

[Hooks documentation](https://zcode.z.ai/cn/docs/hooks) documents tool success/failure events and stop checks, but no dedicated child-start/child-stop lifecycle contract in its event list. Hook configuration is snapshotted at session startup and project-level hooks are ignored in the documented version. Treat hooks as optional supplementary evidence until tested, not a replacement for ORX's own durable assignments.

## CLI uncertainty and local evidence

The official [security response center](https://zcode.z.ai/cn/zsrc) includes a ZCode CLI in its security scope. Consequently, this research cannot prove a CLI does not exist. It also did not find an official installation, headless execution, or agent-lifecycle protocol sufficient to implement a CLI adapter. Third-party projects called zcode-cli or zcode-api are not proof of an official supported harness contract.

Reading `/Applications/ZCode.app/Contents/Info.plist` with PlistBuddy returned installed version `3.14.4`. That metadata is not a test of Beta rollout eligibility or tool behavior. No application internals were reverse-engineered.

## Recommended integration experiment

1. Define named worker and verifier roles through the client, selecting GLM-5.3 and GLM-5.3-Flash explicitly; record their actual generated identifiers and supported reasoning levels.
2. Start a fresh ZCode host conversation with ORX's tools connected. Delegate one harmless assignment and record how child identity, result, errors, and actual model can be observed.
3. Test a worker in an explicitly supplied task directory and a verifier against an immutable target revision. Check actual file paths and Git state rather than relying on context isolation.
4. Test two assignments concurrently, cancellation, approval blocking, parent interruption, and application restart. If lifecycle evidence cannot be recovered, preserve ORX assignment identity and lease state independently and reconcile conservatively.
5. Adopt the integration only for capabilities demonstrated by these experiments. Keep profile intent separate from observed execution identity, model, and effort.

These experiments are proposed acceptance checks, not actions already performed by this research.
