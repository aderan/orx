# 验收证据有效性

验收记录描述某一份交付及其输入。相同输入可以复用已完成检查；输入变化后，旧记录保留为历史，退出当前有效验收窗口。

## 内容版本

每项任务的检查共享一份 verification context，包含：

- 当前 Worker attempt 和计划修订。
- 已声明交付产物的内容与文件权限；没有结构化产物声明的旧执行方式，使用 scope.allowed 作为保守的产物范围。
- preread 文件、目录或 glob 的内容。
- 直接依赖的产物、产出 attempt 和输入版本；变化沿依赖链传播。
- 任务 acceptance、verification 和 scope 契约。

文件以 SHA-256 比较内容，mtime 改变不会单独使验收失效。同大小且恢复原 mtime 的内容修改仍可检测。目录跟踪成员及内容，忽略运行元数据和常见缓存；具体排除项见 [实现](../src/orx/verification_context.py)。缺失文件有明确状态；无法读取、工作区外的符号链接和不支持的文件类型会阻塞验收。

当前按任务粒度失效：任务内的检查共享输入声明，受影响任务的所有检查重新进行；相关下游任务跟随失效，其他任务保留。新 Worker attempt 或新计划修订仍开始新的验收窗口。

## 检查与调度

`orx verify` 和 `orx run` 在推进前比较指纹，并持久化需要的失效记录。`verify` 按依赖顺序检查；依赖尚未重新通过时，下游等待。已派发但未认领的 Worker 也会等待依赖恢复；在途 Worker 不被静默替换。

已通过或因验收失败的任务，在输入变化后可重新进入 verifying。原来的 Worker 交付继续存在，验证失败的修复仍使用正常 retry 流程。已完成 Run 在重新验收期间离开 done，再以新的验证结果收口。取消和暂停规则保持原有约束。

同一内容版本下，命令检查及合法 agent 裁决继续复用；断连、超时或协议错误没有裁决，只重试未完成条目。每次重验使用新的命令日志路径，旧日志不覆盖。

`status --json` 只读检查当前文件：

- `evidence_freshness.stale` 给出陈旧任务和变化路径。
- `verification` 排除这些任务的陈旧通过记录，`result` 为 verification_stale。
- `next_actions` 提供带当前主控声明的 verify 命令。
- `run.status` 和任务状态仍是数据库中的记录状态，直到推进命令完成持久化失效。

## 在途验证器

Verifier attempt 绑定派发时的 context ID。提交或 CLI 返回裁决时再次比较输入；若版本已变，返回 `verdict: null`、`error_kind: evidence_changed` 和重验提示，陈旧 pass/fail 不写入当前验收结果。

原在途 attempt 在其结果返回前保持打开，不重复派发同一条目。它真实返回后，以陈旧执行记录关闭，再由下一次 verify 派发新验证。输入恢复成原内容也不会恢复已经失效的旧记录。

## 历史与兼容

指纹、失效水位和派发绑定追加在 task_events 中；数据库表结构和已有行保持原状。`Store.verifications_current` 同时按 Worker attempt 和 context 水位选择当前有效行。直接统计历史 passed 行的读取端需应用这套过滤规则。

没有指纹的历史验收，在首次推进时重新检查一次。新的交付不会继承无法关联到 Worker 的旧裁决。完成回执的幂等重放仍返回原回执，它不恢复已经失效的当前状态；调用方继续读取 status 和 next_actions。

这是命令入口及裁决返回时的内容核对，不包含后台文件监控、只读沙箱或不可变文件系统快照。应声明完整产物和 preread。验证期间持续修改被检查的源文件会使检查无法收口；未声明且不在产物范围中的外部输入不在本规则覆盖范围内。
