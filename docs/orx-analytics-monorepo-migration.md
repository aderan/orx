# ORX Analytics 同仓迁移与桌面统一方案

本文定义源码导入、应用升级、发布切换和验收。当前执行状态见
[实施计划](../IMPLEMENTATION_PLAN.md)，架构决策见
[ORX ADR-0001](adr/0001-orx-monorepo-independent-packages.md)。

## 目标布局和职责

```text
ORX/
├── pyproject.toml             # orx-agent 包与 orx 命令
├── src/orx/                   # ORX 执行、配置、路由和项目索引
├── tools/orx-analytics/       # 自有 pyproject.toml、src、tests、docs 和 CLI 构建检查
├── apps/macos/                # 现有 SwiftUI 应用、资源、Swift 测试和 App 打包
└── docs/                      # ORX 契约、迁移和联合验收
```

| 入口 | 所有权与依赖 |
|---|---|
| `orx` | ORX 执行、配置和状态。单独安装可运行，Analytics 故障不阻止 ORX 执行。现有 `ORX_ANALYTICS_BIN` 继续是可选接入。 |
| `orx-analytics` | 保留 Python 包名、`orxanalytics` 模块和 CLI 入口。单独安装可分析支持的非 ORX 会话。按只读契约和项目索引读 ORX 数据，不调用 `orx.Store`，也不通过可能触发迁移的 ORX 命令读取源库。 |
| `ORX.app` | macOS 唯一日常桌面入口。通过 ORX 的机器可读配置接口读写策略，通过现有 Analytics 本地协议读取执行与用量。复用现有 App、引擎和界面状态管理。 |

仓库路径与运行时路径分开。0.5.0 将 Analytics 默认目录设为 ORX 用户数据根的 `analytics/`，默认 `~/.local/share/orx/analytics/`。保留 `ORX_ANALYTICS_HOME`、`--data-dir`、项目登记和数据目录内的 socket。保留 `ORX_CONFIG_DIR`、`ORX_DATA_DIR` 和项目配置解析。构建程序从提交树或发布产物识别源码，安装后的 App 和 CLI 不寻找开发机 checkout。

## 阶段 1：锁定基线并导入 Analytics

1. 冻结导入清单。记录两个仓库的完整提交、所选 Analytics 源码对应的包版本、引擎协议和存储版本、历史标签与发布资产。基线调研时 Analytics 本地 `main` 有三条提交领先 `origin/main`，其中包含 0.4.4 的采集与存储修复。执行时重新核对双方差异，明确选用哪个提交及原因。分支名、远程默认分支和本机安装版本都不能单独充当基线。
2. 从选定提交的**已跟踪源码树**导入普通 Git 目录，按目标布局拆分。Analytics 包、测试、指标契约和安装检查放进 `tools/orx-analytics/`。Swift 包、应用资源与 App 构建链归 `apps/macos/`。在导入提交记录原仓库、完整提交、树和路径映射，保留必要的许可证及版权信息。原提交历史由旧仓库保留。导入基线若尚未在旧远程可达，先保存可复验的源快照或 Git bundle 和校验值，再据此导入。
3. 先做机械导入，再在独立提交中调整路径与依赖查找。排除嵌套 `.git`、`.venv/`、`.build/`、`var/`、`.orx/`、本机数据库、会话原文、发布产物和凭据。仓库现有、可说明来源的测试夹具按清单核验后保留。修正源码归属变化导致的 README、指标契约和安装文档链接。

**产物与门禁**：提交可追溯到基线，留有导入文件或内容校验清单与差异说明。从全新 ORX 检出可以单独构建和安装两套包。仅安装 ORX 可以完成确定性的执行验收，Analytics 在没有 ORX 的独立环境可以运行 CLI 和分析夹具。检查无本机私有数据、无 gitlink 和外部 checkout 依赖。旧仓库与已安装应用在本阶段照常使用。

## 阶段 2：适配构建、兼容和联合验收

1. 保留分别构建 ORX 和 Analytics 的 sdist 与 wheel 的入口。将 App 打包脚本所需的 Swift 目录、内置 Python、Analytics 包和版本来源改成显式路径。App 继续从固定来源内置运行时。以干净工作树重复运行包安装检查、Swift 测试和包内引擎冒烟。
2. 为 `scripts/joint_release.py` 增加同仓候选模式。一次冻结 ORX 提交，从同一源码快照构建两个 Python 包和 App。清单记录源码提交、各包与 App 的版本、ORX schema、Analytics store、引擎协议及产物哈希。现有 G011/G012 旧版本复验仍按各自原始双仓组合、原样本和原标签进行。
3. CI 分别运行 ORX、Analytics Python 和 macOS Swift 检查。观测契约、引擎协议、打包路径或跨边界行为变化时，跑联合用例。更新受支持组合的兼容表，覆盖历史数据库、当前数据库和已知不支持的未来 schema。用户仍可能分别升级 CLI 和 App，因此必须验证旧客户端与新引擎、新客户端与旧引擎的兼容结果。不能通信时在界面提示版本差异，并保持原引擎所有权。

**产物与门禁**：各包从自己的构建产物在隔离环境通过安装检查。当前同仓联合验收只需要当前 ORX 检出，历史复验仍按需获取旧仓库。验证源库读取符合只读与 WAL 契约，历史版本的任务身份与用量口径保持一致，未知数据和不支持版本明确可见。

## 阶段 3：复用现有应用并统一为 ORX

用户看到一个 `ORX` 菜单栏入口。保留进行中数量、需关注执行和 Run 详情入口，主窗口提供三个页面：

| 页面 | 首版内容 |
|---|---|
| 执行 | 项目、Run、Task、状态、异常、重试和 Attempt。实际模型和路由原因以当次记录为准，未报告的信息标为未知。 |
| 模型与路由 | 用户默认或具体项目的生效配置、覆盖来源、Controller/Planner/Worker/Verifier 的候选 profile、模型档位、推理强度及回退顺序。Planner 按规划深度分组。 |
| 用量分析 | 复用任务及历史查询，保留 token 来源、覆盖程度和重试、验证分项。ORX 已记录用量与原生会话预览各自展示。 |

先接只读配置预览，以现有 `orx config list --json`、`orx config models --json` 为起点。桌面端必须能为每次请求指定项目和作用域，并明确所调用的 ORX 安装及能力。测试从 Finder 启动的环境，避免依赖终端的 `PATH`、工作目录和 shell 初始化。配置读取不能引发状态库迁移。缺少 ORX 或安装版本不支持时，执行和用量页面仍可消费已有分析数据，配置页说明原因。

再接可编辑项，首轮限于 ORX 已支持且经验证可写的项目/用户默认值、规划深度和候选顺序。由 ORX 校验类型、profile 引用及写入范围。提交前预览目标层和生效值，外部编辑导致草稿过期时提示重新载入，保存后读取实际生效配置。界面说明哪个后续派发会读取变更，不改写已创建 Attempt 或历史模型记录。模型档位、推理强度和规划深度分开呈现，沿用 ORX 当前的深度判定。

**产物与门禁**：同一 Run 能下钻任务用量及当时的模型信息，并打开正确项目的当前路由。双项目测试覆盖不同的项目覆盖值。错误引用、文件并发修改与不支持的 ORX 版本有明确结果，失败保存不留下部分修改。关闭详情仍驻留，通知跳转正确且只打开一处目标窗口。

## 阶段 4：验证安装升级、登录项和数据回退

**应用身份。** 产品显示名称与安装包名称统一为 `ORX`。正式渠道从
`org.orxanalytics.macos` 切换到 `com.aderan.orx`，内部预览从
`org.orxanalytics.macos.dev` 切换到 `com.aderan.orx.dev` 并继续标注
`Internal Preview`。原预览身份在实际安装验收中被当前账户的 macOS
控制中心屏蔽，结果见 [阶段四验收记录](diagnostics/analytics-monorepo/stage-4.md)。
每个新 App 首次启动时仅从同渠道的旧偏好域补入数据目录、刷新设置、通知偏好
和 ORX 可执行文件路径。现有新域值优先。旧偏好域和数据目录保留用于回退。
在系统设置中确认并移除旧登录项，必要时在新版重新授权通知和开启登录启动。

**升级演练。** 对每个拟发布渠道，用其真实旧版产物执行下列顺序。以测试账户和隔离数据目录先演练，再用实际分发包验证干净安装。

1. 记录旧 App 路径、版本、渠道、登录启动与通知偏好，以及 CLI watch 和引擎是否仍有其他客户。记下 analytics 数据目录、registry、游标、配置自定义项和 store 版本。协调停止需要升级的采集写入，创建 SQLite 一致性备份，另保存旧 App 与 CLI 产物。源 ORX 项目无需为仓库迁移而重建或移动。
2. 在旧 App 中关闭其登录启动并退出，核对其注册状态和运行实例。若旧 App 已不可启动，在系统登录项中按路径、渠道和身份识别后人工处理。新版 `ORX.app` 替换旧版，保留自定义数据目录及兼容偏好。确认旧版没有在登录后再次启动，再按用户原偏好或明确选择恢复新版登录启动。必要时提示重新授予通知权限，记录系统实际状态。
3. 验证 App 和 CLI watch 连接同一个 data-dir 对应的引擎。现有 compatible 引擎可继续服务。发现旧版独立 watcher 或不兼容引擎时，显示诊断和协作迁移指引。退出 App 只释放 App 自己的需求。需要更换引擎时由确认的操作者协调停止旧客户端与进程，不根据 PID 或文件名自动终止其他进程。
4. 若升级后要回退，先退出新版并取消其登录项，再核对旧版能否打开当前 store。跨 store 版本时恢复升级前的数据快照到原目录或隔离目录，保留升级后的库供核对。用旧 App 与对应 CLI 启动并恢复登录设置。不要手改 schema 版本或把新旧引擎同时接入正在恢复的数据目录。

**产物与门禁**：以真实旧版验证项目登记、自定义目录、历史/用量和可迁移的偏好均保留。在现有 Apple Silicon、macOS 13+ 支持范围内，验证重复启动、登录和旧包留在磁盘待清理的场景。升级后只有一个日常菜单栏实例，登录启动开启时只有一条生效条目，关闭时无生效条目。验证退出 App 后其他 CLI watch 需求仍存活，并实际完成数据回退演练。有效签名与公证按发布渠道原有要求验证，正式渠道条件不满足时仅可验收内部预览。首个版本以路径迁移和界面整合为主，优先避免顺带变更 Analytics 的 store 或 IPC 协议。

## 阶段 5：切换发布来源并收口旧仓库

1. 先从 ORX 仓库发布通过联合验收的产物，公布 `orx`、`orx-analytics`、`ORX.app` 的版本组合、校验值、安装入口和升级/回退步骤。为 Analytics 提供可独立下载和安装的 wheel 或明确的子目录 Git 安装方式。若提供 Git 安装方式，用实际发布 tag/commit 验证 `tools/orx-analytics` 的安装，旧仓库 Git 安装用户需显式重装到新来源。旧 URL 的 `upgrade` 继续跟踪旧仓库，文档应写明如何识别和切换。
2. 确认新产物可获取且升级回退通过，再在旧仓库 README 首屏和迁移文档写明新位置、最后旧版、安装和 issue 入口。更新两个包的项目元数据及新发布文档。保留旧仓库的提交、历史 tag、历史 release、资产和旧安装链接。旧仓最后提交只做迁移指引，不继续分发新版。
3. 从切换点起由 ORX 仓库接收新问题并发布新版。旧仓留作可读历史镜像。设置 GitHub archive 前先确认迁移指引、历史产物可获取，且无需在旧仓继续维护事项。若暂不归档，在 README 标注维护已迁移，停止旧发布流程。新旧历史标签保持原位，后续 release 清单分别追踪各包版本和实际源码提交。

**产物与门禁**：用户从旧仓首页能找到新的安装入口。从新地址干净安装两个 CLI 和 App 后可查看正确版本，安装来源与已发布校验清单一致。历史 tag 与产物仍可下载，历史安装可回退。新的安装说明与兼容表均通过实际投放产物验证。

## 执行交接与验收记录

执行 agent 按上述五阶段建立 `IMPLEMENTATION_PLAN.md`，逐阶段记录目标、测试、状态和提交。保留单独的导入提交、构建适配提交、桌面功能提交及发布证据。归档受验的版本组合、命令与结果、安装升级演示、失败与回退证据后，按仓库约定移除临时计划。

最终验收应能从同仓干净检出复现：ORX 独立执行、Analytics 独立分析非 ORX 会话，以及用户从旧应用切换到单一 ORX 菜单栏入口，在同一窗口查看任务消耗并修改项目路由。交付结论应写明受验渠道、实际发布状态、旧仓指向与仍存在的兼容限制。
