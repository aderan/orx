# PBV 验证条目写法（Plan IR verification 字段）

每片 verification = ≥1 条命令门禁 + ≥1 条 agent 审查。条目语法三种：shell
命令（项目根目录执行）、`agent: <说明>`、`agent[vision]: <说明>`。

内核会在 verifier prompt 里自动带上：Goal 目标与 constraints、acceptance
全列、该条检查指令、该任务已记录的命令门禁结果、执行证据路径、复验时的
前次问题。所以**条目文本只写检查方法本身**，不重复约束、验收、门禁结果或
前次问题。

## 命令门禁条目（确定性，V0）

用项目最强验收命令；开工前查 Makefile/scripts/CI 确认，不要凭习惯写：

```text
make verify
```

（StockMate 示例；别的仓库可能是 `pytest`、`just check`、CI 等价命令。）

## agent 审查条目（独立验收）

一份条目文本同时覆盖首次全量与修复后复验——内核在复验时注入 prior issues，
审查方据其有无自行切换模式：

```text
agent: 独立验收审查。先看 git diff HEAD 了解本切片全部改动。首次验证做全量：逐条核对验收标准，检查改动是否违反仓库硬约束，必要时读相关源码。若带有前次问题（复验），不重做全量，只核：1) 上轮问题是否逐条解决；2) 修复触及的文件及其直接依赖是否引入新问题（改动文件清单以修复方完成报告为准）；3) 仓库硬约束是否仍满足。给出结论与问题清单（含位置与证据）。
```

要点：

- 复验增量的三条核对（上轮问题逐条解决 / 修复触及文件及直接依赖无新问题 /
  约束仍满足）写死在条目里——内核不感知"哪些文件是本次修复触及的"，靠
  修复方报告改动文件。
- 因此 Controller 纪律：每轮 `orx task complete` 的 evidence summary 必须列
  **改动文件清单**（首次构建与修复轮都是），复验条目依赖它。
- 首次全量与复验增量之外的中间态不存在：要么全量、要么增量，不做"顺手多查"。
- 审查方只报告不修复、不重跑命令门禁（退出码已在它的上下文里）。

## agent[vision] 条目（仅渲染 UI 验收用）

```text
agent[vision]: 对照验收标准核对渲染结果（布局/间距/溢出/状态），给出结论与问题位置。
```

## 常见错误

- 空验证列表——不满足 PBV 完成条件（内核完成即过，skill 层禁止）。
- 只有 agent 审查没有命令门禁，或反之——双门禁缺一不可。
- 条目里复述约束/验收原文——内核已注入，重复浪费 verifier 上下文。
- 门禁命令写弱了（如只跑 lint 不跑测试）——用项目最强命令。
